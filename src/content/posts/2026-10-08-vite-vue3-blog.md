## 起因：手写方案的三个死结

第一版博客没有框架、没有构建工具，就是一个 `index.html` 加几个 `.css` 和 `.js`。刚开始很舒服，改一行刷新就能看到。真正难受起来是在第三个页面之后。

### 导航和页脚要改三遍

`index.html`、`about.html`、`projects.html` 各有一份完全相同的导航结构。想把「关于」挪到「作品」前面，就得改三遍，而且总有一遍会手滑写坏缩进。

### 暗色主题的样式会打架

每个页面各有一份 `theme.js`，各自读 `localStorage`、各自切 `data-theme`。切页面时偶尔闪一下白屏，排查了半天是因为某一页的脚本放在了 `</body>` 之后。

### 内容混在结构里

文章的正文直接写在 HTML 里，写一篇新文章要复制一整段 `<article>` 骨架，再逐个改标题、日期、摘要。漏改一处，文章列表和详情页就对不上。

## 换到 Vue 3 之后

Vite 起项目很快，`npm create vite@latest` 之后基本不用配什么。真正解决问题的其实是这两件事。

### 布局只写一次

`App.vue` 里放导航和页脚，路由出口放中间：

```vue
<template>
  <div class="app-shell">
    <SiteNav />
    <main class="app-main">
      <RouterView />
    </main>
    <SiteFooter />
  </div>
</template>
```

改导航只需要动 `SiteNav.vue` 一个文件。

### 内容变成文件，而不是代码

这是收益最大的一处。文章放在 `src/content/posts/` 下的 `.md` 文件里，构建时用 glob 一次性收进来：

```js
const modules = import.meta.glob('../content/posts/*.md', {
  query: '?raw',
  import: 'default',
  eager: true,
})
```

于是「写一篇文章」这件事退化成了「新建一个文件」。列表页、首页的最新列表、按年份分组，全都从同一份数据派生出来，不可能不同步。

## 换来的是什么，代价是什么

变轻松的部分：

| 事情 | 手写方案 | Vue 3 + Vite |
| --- | --- | --- |
| 改导航 | 改 N 个文件 | 改 1 个组件 |
| 发新文章 | 复制 HTML 骨架 | 新建 .md |
| 主题切换 | 每页各一份脚本 | 一个 composable |
| 部署 | 直接拷文件 | 跑一次 build |

代价也很实在：

- **多了一层构建。** 改完文件要等编译，只是改个错别字也得等一两秒。
- **多了一套依赖。** `node_modules` 有几百兆，升级 Vite 大版本时可能要顺手改配置。
- **多了一个陌生人的调试成本。** 现在出了问题，得先想清楚是 Vue 的问题还是自己代码的问题。

## 一个具体的小坑：hash 路由

GitHub Pages 是纯静态托管，没有服务端 rewrite。用 history 模式的话，直接访问 `/posts/xxx` 会拿到 404——因为服务器上确实没有这个文件。

所以这里用的是 hash 路由：

```js
const router = createRouter({
  history: createWebHashHistory(),
  routes,
})
```

URL 里带个 `#` 不好看，但 `#` 后面的部分不会发给服务器，刷新、分享链接、直接粘贴地址都不会 404，也不需要维护 `404.html` 的重定向脚本。对这个规模的站点来说，这笔买卖划算。

## 小结

如果一个站点只有两三个静态页面、一年也不改几次，手写确实更省事，也更快。但只要出现「重复的骨架」和「反复新增的内容」这两个信号，组件化加构建工具带来的收益就会很快超过它的成本。

这次重写的教训是：**别在手写方案里硬撑。** 该换的时候换，换完确实省事。
