## 项目背景

我在几个平台上都有零散的音乐文件，想有一个统一的、能自己控制的播放界面，而不是每次点开不同的客户端。

做它的另一个理由是练习 Web Audio API：进度条、音量、频谱这些看起来简单的控件，背后都在跟音频上下文和渲染时序打交道，很适合拿来把这块补上。

## 做了什么

做成的是一个跑在浏览器里的音乐播放器，没有服务端，整个曲库由构建时的静态资源构成。

- **播放列表管理**：支持多列表并行，拖动排序，列表存在 `localStorage` 里，刷新不丢。
- **歌词同步滚动**：解析标准 LRC 格式，按时间戳定位当前行并自动居中；点击任意一行可直接跳转到该时间点。
- **频谱可视化**：基于 Web Audio API 的 `AnalyserNode` 取频域数据，用 Canvas 绘制，支持柱状和波形两种样式。
- **键盘操作**：空格播放/暂停，左右方向键快退快进 5 秒，上下方向键调音量，`L` 切换循环模式。

## 难点与取舍

### 音频状态与 UI 状态分离

播放器的状态很碎：当前曲目、播放进度、音量、循环模式、列表顺序。如果全部塞进一个响应式对象，任何一次拖动进度条都会触发整个界面重渲染。

这里拆成了两层：音频相关的实时数据（`currentTime`、频谱数据）走 `requestAnimationFrame` 直接写 DOM 或 Canvas，不进响应式系统；只有真正影响结构的（当前曲目、列表内容、循环模式）才放进 `ref`。进度条拖动时不再有卡顿。

### 频谱绘制的性能陷阱

第一版用 `setInterval` 每 30 毫秒重绘一次 Canvas，结果在低配笔记本上风扇狂转。

改成 `requestAnimationFrame` 之后依然不理想，最后发现问题在尺寸：Canvas 的 `width` / `height` 属性没跟着 CSS 尺寸走，实际渲染分辨率是显示尺寸的三倍，等于每帧多画了九倍的像素。用 `devicePixelRatio` 校准、并给 DPR 设上限 2 之后，CPU 占用降到了原来的三分之一左右。

### 已知取舍

- 只支持本地文件，没有接入任何在线音乐源，因为版权和接口稳定性都不好把握。
- 没有做移动端的后台播放，切到别的标签页时浏览器可能挂起 `AudioContext`。
- 波形样式在高频段不够细腻，受限于分析窗口大小，暂时没有再优化。

**本站 Demo 已部署到 Vercel，点击"在线体验"即可使用完整功能（搜索/播放/歌词/歌单/榜单），不依赖本地代理。**

### 本地开发（可选）
想在本地体验完整功能，需在另一个终端运行 Node 代理：
```bash
cd D:\my-music
npm run server
```
代理启动后，博客开发服务器（`npm run dev`）的 Vite proxy 会自动将 `/api` 请求转发到本地代理（端口 3001），在线播放和搜索即可正常工作。
